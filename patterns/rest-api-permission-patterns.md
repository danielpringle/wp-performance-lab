# REST API Permission Patterns (Nonce-Based Authentication)

## Goal

Secure custom REST API endpoints using WordPress nonces
to protect against CSRF and ensure request legitimacy
for frontend-driven interactions.

This pattern is commonly used for:
- frontend collectors (analytics / performance reporting)
- authenticated UI interactions
- editor-side tooling
- internal plugin communication

---

# Example Implementation

```php
public function register_rest_routes() {

    register_rest_route(
        'perf-lab/v1',
        '/report',
        [
            'methods' => 'POST',
            'callback' => [$this, 'receive_report'],

            'permission_callback' => function( $request ) {

                $nonce = $request->get_header( 'x_wp_nonce' );

                return wp_verify_nonce(
                    $nonce,
                    'wp_rest'
                );
            },
        ]
    );
}
```

---

# How This Pattern Works (Lifecycle)

This pattern relies on a 3-stage flow:

---

## 1. Nonce Generation (PHP → Frontend)

A nonce is generated server-side using WordPress core:

```php id="n0v8qp"
wp_create_nonce('wp_rest');
```

It is then exposed to frontend JavaScript via script localization:

```php id="q7m1lz"
wp_localize_script(
    'perf-lab-collector',
    'dpukPerfLab',
    [
        'restNonce' => wp_create_nonce('wp_rest'),
    ]
);
```

### Result

The nonce becomes available in JavaScript:

```js id="j4k9wp"
window.dpukPerfLab.restNonce
```

---

## 2. Nonce Transmission (Frontend → REST API)

The frontend sends the nonce with each request:

```js id="v2k8lm"
fetch('/wp-json/perf-lab/v1/report', {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json',
        'X-WP-Nonce': window.dpukPerfLab.restNonce
    },
    body: JSON.stringify(payload)
});
```

---

## 3. Nonce Verification (REST API → PHP)

The REST endpoint validates the nonce:

```php id="r8p1xq"
$nonce = $request->get_header('x_wp_nonce');

return wp_verify_nonce(
    $nonce,
    'wp_rest'
);
```

If valid:
- request is processed

If invalid:
- request is rejected (401/403)

---

# Summary of Flow

The full lifecycle is:

```txt id="flow1"
PHP generates nonce
        ↓
Nonce exposed to frontend JS
        ↓
Frontend attaches nonce to REST request
        ↓
REST API verifies nonce
        ↓
Request is accepted or rejected
```

# What This Pattern Provides

## Security Benefits

- protects against CSRF attacks
- ensures requests originate from WordPress context
- prevents external forged POST requests

---

## Architectural Benefits

- keeps frontend lightweight
- avoids cookie-based complexity in JS
- integrates naturally with WP REST API
- works without external auth systems

---

# Important Clarification

## Nonce ≠ Authorization

A valid nonce only proves:

- the request came from a valid WP session
- the request was generated by the site

It does NOT determine:
- user permissions
- role-based access
- capability restrictions

For sensitive operations, combine with:

```php id="c9l2wq"
current_user_can('edit_posts')
```

---

# When This Pattern Is Appropriate

Use this pattern for:

- frontend analytics collectors
- performance reporting endpoints
- UI interaction logging
- non-sensitive logged-in features
- editor tools

---

# When This Pattern Is NOT Enough

Do NOT rely on nonce-only validation for:

- admin settings changes
- user data modification
- privileged operations
- financial or external system actions

---

# Common Anti-Patterns

## 1. Treating nonce as authentication

Nonce is not a login system.

---

## 2. Using global open endpoints without checks

```php id="a8m2v1"
'permission_callback' => '__return_true'
```

Only acceptable for:
- public read-only data

---

# Pattern Insight (Important)

This architecture separates concerns:

| Layer | Responsibility |
|---|---|
| nonce | request validity |
| session | authentication |
| capabilities | authorization |

Most secure WordPress systems combine all three depending on context.
